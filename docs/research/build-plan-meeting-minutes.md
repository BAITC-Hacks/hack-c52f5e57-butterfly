# План Butterfly: Nemotron, Telegram и Fly за 2 часа

Обновлён 2026-09-23 по готовому исследованию и указаниям владельца. Лимит исполнения — **120 минут**, из них **75 минут на сборку и проверки + 45 минут неприкосновенного резерва на freeze, публикацию и репетицию**. T+0 — старт исполнения этого плана. Подтверждён относительный лимит; календарное время сдачи не задано.

В общем плане **S2 / doing**: другая сессия ведёт подготовку Brev. Кодирование приложения в этой задаче ещё не начато. По последнему указанию владельца сначала публикуется план; кодирование начнётся отдельной командой. **Nemotron настраивает другая сессия, интеграция выполняется в конце сборки.** S0–S1 завершены документально; приложение, GPU inference и интеграции ещё не проверены. Старые 330 минут оставшейся работы не помещаются в новый лимит. Предыдущий S2 отмечен failed по причине смены бюджета; история сохранена в [архиве](archive/build-plan-before-2h-r4.json).

## Обязательный результат

Одна постановочная встреча RU/KK/mixed → реальная транскрипция со спикерами → Nemotron извлекает поручения с цитатами → пользователь подтверждает владельцев/сроки → скачивает PDF/DOCX. Fly показывает события обработки и проверки; Telegram сообщает о завершении. Публичный frontend — Vercel в финале, backend и inference — собственная GPU VM в Brev.

**Telegram и Fly входят в обязательное публичное демо.** Возможность отключить их нужна для устойчивости core и offline-профиля и не означает, что их можно молча исключить из демонстрации. Nemotron — основной провайдер; точную модель и API передаст сессия настройки Brev. До подключения применяется явно помеченный demo/manual-transcript режим. Он не засчитывается как реальный inference.

## Проверяемый сценарий

Пути и команды ниже — контракт будущей реализации; сейчас в репозитории их ещё нет.

- **Input:** `demo/meeting-ru-kk.wav`, постановочный клип 60–90 секунд с двумя спикерами и RU/KK фрагментами; `demo/meeting.json` со списком участников, датой и timezone `Asia/Almaty`; `demo/expected.json` с тремя поручениями: два с явными владельцами/сроками, одно с неизвестными владельцем/сроком, плюс отменённое поручение, которое не должно попасть в результат. Только синтетические сведения.
- **Action:** после запуска стека выполнить `sh scripts/demo-smoke.sh --fixture demo/meeting-ru-kk.wav --metadata demo/meeting.json --expected demo/expected.json --profile public-demo`; затем повторить те же действия в UI: upload → обработка → сопоставление спикеров → подтверждение поручений → экспорт. Скрипт должен загружать файл в реальный pipeline, а не возвращать эталон.
- **Expected core:** завершённый job с transcript, непустыми текстом/таймкодами/метками спикеров; три поручения, у каждого цитата и интервал внутри записи. У двух явных поручений владелец и срок совпадают с эталоном; у неопределённого поля null и `needs_review=true`; отменённое поручение отсутствует. После пользовательского review скачиваются открываемые PDF и DOCX, содержащие подтверждённые поручения и кириллический текст.
- **Expected Nemotron:** manifest и run-log содержат точный model ID, revision, runtime, GPU/VRAM, длительность и статус реального запроса к собственному endpoint Brev. Внешний hosted inference не используется.
- **Expected Fly:** поток событий с `job_id` и `event_id` показывает uploaded → transcribing → extracting → needs_review → completed; подтверждение/исправление поручения создаёт один feedback для этого действия. Повторная доставка одного event ID не повторяет feedback.
- **Expected Telegram:** в разрешённом демо-чате работает `/status`, приходит уведомление completed с job ID и ссылкой; повтор успешно обработанного события не создаёт второе сообщение. `/unsubscribe` прекращает уведомления. В доказательствах сохраняется message_id, но не токен.
- **Artifacts:** `data/results/demo-run.json`, transcript/actions JSON, PDF/DOCX, журнал событий, Telegram receipt и manifest моделей. Эти runtime-файлы не публикуются автоматически в GitHub. Доказательства демо прикладываются в отдельный очищенный bundle.
- **Negative gate:** недоступный GPU даёт явный failed, неизвестный chat/user не получает сведения о встрече, выключенные Fly/Telegram не ломают core. Offline-проверка использует заранее скачанные веса и локальные frontend/assets.

## Минимальная архитектура

Frontend Vercel → HTTPS API Brev → ограниченная очередь на одну встречу → ASR/диаризация → Nemotron → review → экспорт. Файл загружается прямо в backend. Worker выполняет модели последовательно; формат действий валидируется на сервере, неизвестные поля требуют подтверждения. Метки speaker не подменяют имена участников.

Один журнал job-events обслуживает UI и Fly; outbox обслуживает Telegram. Event IDs позволяют проверять соответствие визуализации реальным действиям. Для неопределённого результата отправки Telegram состояние фиксируется отдельно: абсолютная exactly-once доставка по сети не обещается.

## NVIDIA Nemotron на Brev

Настройку выполняет другая сессия. Эта сборка не меняет её VM, веса или Launchable. Сначала реализуются независимые frontend/API/worker и интерфейс провайдера; реальный endpoint подключается последним перед финальными проверками.

Handoff от сессии настройки: доступный backend endpoint, протокол ASR/file API, OpenAI-compatible LLM base URL (если такой контракт предоставлен), точный model ID/revision, внутренние health checks, таймауты и способ серверной авторизации. Секреты передаются через окружение, не через GitHub. Готовый voice UI сам по себе не заменяет batch API встречи.

Model ID не фиксируется заново этим планом: прежний кандидат Nano 9B v2 и Qwen3-4B из ресерча не переопределяют модель, выбранную в сессии настройки. По результатам подключения фиксируются фактические runtime, VRAM, latency и качество RU/KK/mixed. Облачный inference не используется как скрытая замена собственного endpoint Brev.

До подключения разрешены только честно обозначенный synthetic-demo и работа с вставленной стенограммой. Пользовательская аудиозапись без доступного ASR не получает выдуманную расшифровку. Если endpoint не готов к финальной интеграции, это явно отражается в статусе и демонстрации.

## Telegram и инновационное демо Fly

Telegram: один разрешённый synthetic-demo чат, long polling в отдельном worker, `/help`, `/status`, `/subscribe`, `/unsubscribe`; завершение/ошибка job. Авторизация chat + user, сохранение offset/subscriptions, дедупликация, ограниченный retry/обработка retry_after. Уведомления содержат только статус, job ID и ссылку; содержание встречи не копируется. Токен только на сервере. Live evidence пока отсутствует. [Telegram Bot API](https://core.telegram.org/bots/api).

Fly: переиспользовать существующую визуализацию событий. Если 3D assets не готовы, использовать компактную 2D Fly-визуализацию с реальными состояниями и кнопками review. В демо рекомендация «проверить владельца/срок/цитату» объясняется отсутствующим полем; feedback отражает реальное подтверждение/исправление. Offline assets локальные; provenance и лицензии сохраняются.

Инновационная гипотеза: Fly помогает замечать непроверенные поручения и объясняет выбор следующего действия. До сравнительного измерения это гипотеза. Не заявлять обучение нейросети, повышение качества ASR или измеренное преимущество. Если adaptive routing не реализован, обозначить Fly как событийную визуализацию проверки.

## Что сокращено до следующих итераций

- Подключение ботом к Teams/Zoom/Meet, календарь и трекеры: отложены; обязательность meeting-bot по ТЗ остаётся открытым вопросом организаторам.
- Длинные встречи, восемь полноценных benchmark-клипов, fine-tuning и сравнительный A/B эксперимент Fly: отложены; один демо-клип не доказывает общее качество.
- Восстановление анатомических 3D meshes и визуальный полиш: отложены при отсутствии готовых assets.
- Продакшен SLA, нагрузочное тестирование, enterprise SSO и сертификация закрытого контура: вне этого двухчасового демо.

Сохраняются core-сценарий, проверка неопределённых поручений, оба экспорта, реальный Nemotron-run, минимальные Telegram и Fly, изоляция ошибок и воспроизводимые доказательства. Сокращение optional-полиша не позволяет отметить обязательные проверки done без результата.

Следующее действие после отдельной команды владельца: продолжить **S2** кодированием приложения, уложить локальный каркас и контракт провайдера в 15 минут; подключить Nemotron последним. Планирование и публикация документации не засчитываются как выполненная сборка.
